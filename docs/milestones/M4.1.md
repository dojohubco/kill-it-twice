## Byte contract and minimal proposed correction

One normal consumer transaction admits at most 32 ORIGINAL received messages and at most 1048576 bytes of their canonical AMQP body buffers, including the canonical body/hash wrapper. Equality is admitted. Deduplication may reduce SQL unique items but never reduces the application's original retention charge. For valid unique inputs SQL must charge the exact canonical wire bytes and therefore no more than the admitted original messages.

Add migrations/consumer/002-batch-byte-accounting.sql. Preserve migration 001 byte-for-byte. Replace only consumer.process_batch's accounting using octet_length of bytea concatenation: UTF-8 '{"body":' + decoded canonical body + UTF-8 ',"content_sha256":"' + the validated hash + UTF-8 '"}'. Do not change 1048576/32, isolation, ordering/locks, effects/projection/inbox logic, ownership, fixed search_path, SECURITY DEFINER or grants/PUBLIC revocation. No row or historical evidence is rewritten. No generic splitter or P6002 quarantine policy.

The 1 MiB number is not total JS heap, metadata, protocol frames or SQL parameter size. Existing transport/quarantine cap 128 KiB, canonical per-record 64 KiB, prefetch 64, and relevant metadata <=4 KiB remain distinct. Raw prefetch retention is bounded by 64*128 KiB; selected metadata by 32*4 KiB. Valid selected canonical/decoded copies remain bounded by original received count/bytes. The hex SQL representation is at most twice unique body bytes plus a fixed bounded 32-item JSON/hash framing overhead. These are representation bounds, not measured capacity conclusions.
