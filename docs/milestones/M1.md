# M1: Source capture contract

Status: authorized before implementation; evidence pending.

The following scope and test matrix are copied from the authorized task. Passing M1 is not a full G1-G5 result. SPEC v1 and the initial ADRs retain their pre-implementation AI-assisted review provenance and authority.

C. IMPLEMENT ONLY THE SOURCE CAPTURE CONTRACT

Objective: prove that supported source state changes and immutable source-owned revision evidence commit atomically, remain protected from runtime bypass, and retain late commits independently of allocation order.

Implement only a minimal source schema and source mutation helper. A small source-identity/configuration table plus entities and outbox tables is appropriate. Do not precreate the full future pipeline schema. Before executing the migration, state in docs/milestones/M1.md which SQL constraints, triggers, grants, and transaction boundaries enforce the M1 requirements.

Required behavior:

- A migration-owned persisted source epoch survives ordinary reconnect/restart. Entities have database-owned positive BIGINT identity, increasing per-entity version, source change identity, source-recorded time, deletion state, and full payload or a tombstone. IDs/versions returned to TypeScript are handled without Number rounding. Enforce an explicit representable version bound; overflow fails rather than wraps.
- Meaningful insert, payload update, logical delete, and explicit restore create source-owned revisions. Insert begins at version 1; each meaningful later row mutation increments by one. An exact no-op produces no new revision/outbox event. Two meaningful changes in one transaction remain two revisions if the transaction commits; rollback removes both.
- Delete retains identity/version and emits a tombstone with no live payload. Restore uses a supplied live payload and a higher version, not a reused identity or reset version. Enforce payload/deletion consistency.
- The trigger writes a complete immutable after-image with stable (source_epoch, entity_id, entity_version) uniqueness and source change identity in the SAME source transaction. Allocation IDs may order test observations but must never be used as commit watermarks.
- Runtime mutation credentials must not own the tables/schema, be superuser, assume the migration role, choose protected epoch/entity/version/change metadata, edit or delete outbox content, physically DELETE/TRUNCATE entities, or disable capture. Exercise actual runtime-login connections, not only administrator connections with application checks. If privileged trigger functions are needed, restrict their owner/search_path/EXECUTE privileges and test the boundary.
- Historical outbox images remain unchanged after later source updates. Reject unsupported SQL operations explicitly rather than silently broadening the supported mutation surface.

M1 fixtures are tiny ordinary captured source mutations. There is NO baseline seed/activation subsystem yet, no retrying source command API, and no claim of command-idempotent client retries. Do not introduce a fake staged flag or acknowledge events without a pipeline. Source command idempotency, canonical wire serialization/hashing, outbox leases/ACKs, cross-database staging and sink intents belong to M2.

An allocation-order characterization may query the immutable outbox with known test identities. It must not implement a deliberately incorrect production cursor to create a fake later discovery. No production incremental reader/acknowledger is required in M1.

D. REQUIRED TESTS AND ACTUAL FAULTS

Use independent SQL observations of persisted rows/constraints and explicit expected values, not only assertions against helper return values. All required PostgreSQL tests must run on real PostgreSQL with normal durability.

T01 Mutation lifecycle: insert -> update -> no-op -> logical delete -> restore. Assert exact versions, identities, deletion/payload content, source metadata, outbox after-images, and uniqueness. No-op creates nothing. IDs/versions round-trip exactly, including a boundary fixture that would expose unsafe Number conversion.

T02 Transaction rollback: roll back a meaningful mutation and then multiple mutations. Assert the original entity state remains and no corresponding outbox revisions persist. The writer's transaction must have reached the relevant SQL before rollback.

T03 Outbox-side failure: cause a narrowly scoped real database error when an outbox INSERT is attempted, using isolated test-only database instrumentation. Assert the source mutation also rolls back. Do not disable capture or replace the trigger with an application mock. Clean up the instrumentation.

T04 Concurrent revisions: use separate connections/processes to update one entity. Hold the first transaction after its update, demonstrate the other is actually waiting on its lock using backend/session evidence, then release it. Assert unique successive revisions, matching after-images, and correct final state. Fixed sleep delays are not concurrency proof.

T05 Immutability: after later updates, earlier outbox payload and metadata remain byte/field-equivalent to the recorded expected values. Runtime attempts to edit/delete that evidence are rejected.

T06 Runtime privileges: connect as the real application writer and prove attempts to set protected metadata, reuse identity, physically delete/truncate, bypass/disable capture, or escalate role are rejected. Record the effective/session role and ownership checks. Do not claim protection against a malicious database owner.

T07 Commit-order characterization: transaction A creates an outbox entry and remains open; transaction B on another entity obtains a later allocation ID and commits. An independent observer sees B but not A. Commit A, then assert both immutable event identities are present and A's allocation ID is lower. A test-only unsafe "greater than B" query must demonstrably omit A, explaining why production may not use that watermark. This tests a KNOWN architectural risk, not a new discovery. It does not yet prove incremental capture completeness.

T08 Real pre-COMMIT SIGKILL: a child writer performs the mutation/trigger within a transaction and reaches barrier source.after_mutation.before_commit. The parent independently confirms it is at the intended boundary, sends SIGKILL to that exact writer PID, records the actual signal exit, waits for its PostgreSQL session/transaction to end, and asserts no partial source/outbox commit. Then prove a fresh writer can make progress. Kill must not be implemented as throw, rollback, a signal handler, or a mocked connection error.

T09 Real post-COMMIT SIGKILL: the child executes COMMIT, reaches private barrier source.after_commit.before_caller_success, and blocks before sending its ordinary caller success response. The parent independently reads the committed entity and outbox revision, SIGKILLs the child, then reconnects and confirms both still exist unchanged. Barrier telemetry is not the normal caller success channel. Record that caller outcome is unknown despite database success. Do not blindly repeat the mutation or claim command idempotency is implemented.

T10 Repeatability/isolation: rerun the full M1 integration command with new resource names and verify correct cleanup, no cross-run contamination, no leaked writers, and retained sanitized evidence. Test timeouts/barrier failures must fail closed with diagnostics, not become skips/PASS.

Private IPC/test-only barriers may coordinate exact timing. They must carry run/session/entity identity, use bounded waits, and never fake a database result. Actual faults are the SIGKILLs; do not expose a public failpoint API or mount the Docker socket into business code.

Acceptance requires all implemented M1 contract tests to pass on the pinned real service, actual signal/boundary evidence for both kills, direct SQL correctness evidence, and a successful fresh repeat. Passing M1 does NOT establish pipeline delivery, restartable backfill, sink convergence, consumer deduplication, performance, or any full Optio gate.


## Execution boundary

Use a minimal root TypeScript/Node workspace, explicit pg SQL, one isolated real PostgreSQL source service, temporary credentials, ephemeral ports, bounded waits, and owned-resource cleanup. Target and pin Node 24 and PostgreSQL 18. Do not install privileged host software or publish/push. Keep sanitized logs under ignored artifacts/m1/<run-id>/.

Run npm ci, npm run typecheck, npm run lint, npm run test:unit, npm run test:integration:m1, make verify-m1, and make verify; repeat make verify-m1 on fresh resources. make verify must report G1-G5 NOT IMPLEMENTED and exit nonzero. Preserve chronological commits and actual failed evidence. Report tested SHA and final HEAD separately; prepare an ignored review bundle with final tracked snapshot, full diff since the specification commit, evidence, and checksums.

Stop after M1. No pipeline database, canonical ledger, source acknowledger, command-retry API, backfill, Elasticsearch, RabbitMQ, consumer, NestJS API, Angular UI, job scheduler, full gate harness, large seed, or benchmark. Source contract enforcement details must be recorded below before executing the migration.
