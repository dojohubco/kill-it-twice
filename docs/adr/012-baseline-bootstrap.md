# ADR 012: retained baseline bootstrap and atomic activation

Date: 2026-09-20. Status: authorized design before implementation; acceptance pending. This implements planned baseline state and the known baseline/no-op receipt integration obligation. ADRs 005–011 and canonical bytes remain unchanged.

## Source model and compatibility

Forward source migration 006 preserves migrations 001–005 and consumer accounting 002. Add three source-owned tables, with no duplicate mutation ledger:

- bootstrap_manifest: singleton boolean PK CHECK true; source_epoch UUID UNIQUE FK source_identity; phase text NOT NULL in unselected/bootstrapping/sealed/active; origin text in fresh/legacy; bootstrap_key UUID UNIQUE nullable; recipe_version integer, seed text (bounded 128 UTF-8 bytes), requested_count BIGINT (1..2000000), chunk_size integer (1..128), baseline_at finite timestamptz, completed_count BIGINT >=0, sealed_at/activated_at finite timestamptz nullable. Explicit IS TRUE shape checks distinguish unselected/legacy-active from a configured manifest. Config/key/time never change after selection. Phase/progress only advance; active never reopens. No runtime delete/truncate/direct update.
- bootstrap_chunks: bootstrap_key UUID + first_ordinal BIGINT PK, item_count integer 1..128, committed_at finite timestamptz; FK manifest; immutable. Start/end must match declared fixed chunk boundaries. Receipt records seed progress, not a pipeline checkpoint. Deferred validation requires exactly the corresponding ordinal set and matching baseline evidence.
- baseline_revisions: PK(source_epoch,entity_id,entity_version), UNIQUE(bootstrap_key,ordinal), entity FK; version fixed 1, change_id constrained SQL NULL, is_deleted false, recorded_at finite and payload non-null JSONB object; bootstrap_key/ordinal/chunk_first identify manifest/chunk (deferred chunk FK). Immutable update/delete/truncate guards. Metadata/time/payload/ordinal must match the declared recipe and manifest, checked by the database. The original baseline survives current-row mutations.

An already populated source or registered capture binding is initialized as legacy active, with no baselines or fabricated bootstrap manifest parameters. All existing rows/identities/receipts/ACKs are preserved. An entirely unused source becomes closed unselected; that is not permission to seed: a dedicated controlled initialization credential must explicitly choose a matching manifest. No epoch reset, TRUNCATE or sequence reset exists. Empty setup can explicitly choose a zero-baseline activation route only if separately needed; M5A's CLI always requires a positive declared seed count. A missing lifecycle row fails closed.

Current entities permit change_id NULL only for a database-verified retained baseline version 1. The revision kind is derived from that protected identity: NULL means baseline, otherwise mutation. SourceRow types admit real NULL and expose no caller-controlled version. Outbox change IDs remain NOT NULL and all its rows remain mutations.

Replace the command result's outbox-only FK with the existing deferred completion trigger extended to require an exact immutable history match: mutation results join outbox with the non-null change ID; baseline results join baseline_revisions with NULL change ID and version 1. Match epoch/entity/version, time, deletion and JSONB payload using NULL-safe comparisons. Shape checks explicitly reject incomplete/NULL result loopholes. A completed receipt with neither/wrong history fails P2003; successful receipts remain immutable. Old completed rows are validated on migration without updating their values. No receipt is created by seed insertion.

## Non-spoofable bootstrap capability and lock order

Create source_bootstrap NOLOGIN/NOINHERIT as the separate controlled login capability, with CONNECT/USAGE and EXECUTE only begin/status/chunk/seal/activate operations. A private source_seed_owner NOLOGIN/NOINHERIT owns only the seed-chunk definer and has the exact table/sequence/function privileges it requires, never membership granted to runtime. Ordinary source roles cannot SET ROLE into either owner or invoke private seed work.

The common entity preparation trigger becomes SECURITY INVOKER with fixed pg_catalog,pg_temp search_path. It distinguishes the effective database role of its actual definer caller, not a custom GUC or caller metadata. Ordinary create/mutate are source_owner-definer calls and produce UUID mutations. Only the private seed definer executes INSERT as source_seed_owner; it can assign source-owned version 1/NULL change/time from the locked manifest. The capture trigger remains enabled: it retains that seed revision in baseline_revisions, and sends all ordinary changed revisions to the original outbox. Runtime cannot directly INSERT entities, forge metadata or disable capture. Owner/admin bypass remains excluded.

All controlled transitions/chunks lock the singleton manifest FOR UPDATE first. Ordinary READ COMMITTED create/mutate/execute_command acquire FOR SHARE before entity/key locks, including early no-op/replay paths, and require active. Shared locks permit unrelated active writers concurrently. Fixed order: lifecycle -> command/entity or chunk -> outbox/capture binding as applicable. Activation's exclusive lock waits for conflicting transitions; a writer arriving during activation waits, then reads the committed active row. Fresh statements in VOLATILE functions provide READ COMMITTED visibility. Snapshot writers cannot bypass a closed phase; state-changing snapshot mutations retain SQLSTATE 25001 enforcement before enqueue lookup. Read-only observations do not take an ordinary-write capability; existing legacy no-revision no-ops in an already active snapshot retain their original treatment.

## Bounded resumable generation

Manifest selection persists caller expected epoch, UUID bootstrap key, recipe version 1, seed, requested count, chunk bound and database clock baseline_at before chunks. Mismatched parameters fail P7002. The deterministic recipe uses ordinal/seed to vary valid name/country/loyalty_points, arrays/nulls/Unicode and precise unindexed high integers/long decimals, plus roughly 1-KiB ASCII padding. SQL JSONB owns its textual codec. This is configuration, not a scale benchmark.

Each chunk is one short owned READ COMMITTED transaction. Validate explicit first ordinal and declared fixed size/end; lock manifest; return an already committed matching chunk from durable membership or require the next expected chunk in bootstrapping. Generate a bounded set with generate_series and INSERT SELECT, retaining each generated entity ID through the baseline trigger. Insert immutable chunk receipt and advance completed_count in the same transaction. Deferred checks reject incomplete/mismatched membership. Sequence gaps after rollback are allowed. Concurrent identical requests serialize and replay; no caller supplies entity IDs/versions/time or a replacement bootstrap key. Existing chunk replay can recover committed evidence after seal/activation, but no new chunk can be accepted there.

The facade reuses TransactionOwner and allowlisted expiring operations. No raw client, pool, automatic retry or whole-seed transaction. CLI explicitly resumes chunk-by-chunk from status; it never reseeds or selects a replacement key after ambiguity. Output is bounded metadata; mapping reads are limited to one chunk. SQL/hex/driver overhead is separately bounded; established capture/wire/message limits are unchanged.

## Sealing and activation

Seal locks the manifest, requires all declared ordinals with matching recipe/baseline/chunk evidence and exact progress, then records sealed_at. Counts alone do not prove completion. No further baseline insertion is permitted. Repeated identical seal is harmless.

Before activation, controlled application setup reads/validates the expected pipeline ID, epoch and frozen codec outside the source transaction. The source activation operation locks the sealed manifest, invokes the existing register_capture for that exact identity, and changes phase to active in the same source COMMIT. Identical active reentry verifies the retained binding; another pipeline fails. The source function enforces local identity/shape but cannot authenticate remote durability. No downstream transaction or network call is inside source activation. A crash leaves sealed/unregistered or active/bound, never bootstrap-active without capture protection. Legacy active upgrade keeps its original binding and cannot enter bootstrap.

Baselines never enter outbox/capture_work, so a zero mutation backlog says nothing about baseline replication. The CLI reports seed phase/progress, not replicated completion. Startup never stages/publishes all seed rows. Extend SourceReader with explicit <=16 immutable baseline keys, preserving 64-KiB record/256-KiB SQL pre-transfer bounds and exact payload::text/UTC-microsecond exports. Current kind follows its actual change identity. A missing baseline is missing, never substituted from current state.

## Independent evidence and limits

The BS inventory is committed before production changes. A small 257-row multi-chunk fixture uses independently declared recipe/ordinals and explicit mutation journal. Only selected baselines are staged through existing Pipeline.stage and real sinks. Baseline inbox/projected state has a zero-unit aggregate row and no effect; later mutations have ordinary effects. Higher mutation/tombstone first, old baseline later must preserve current projections while retaining distinct publication/inbox evidence. Pre/post chunk and activation SIGKILL each have healthy controls and independent transaction/state observers. Populated M4.1 upgrade and fresh initialization are separate profiles. No automated backfill/range scanner, pipeline run/checkpoint/fence, seed scale acceptance or full G1–G5 claim.
