# ADR 011: RabbitMQ confirmation and independent transactional consumer

Status: authorized design before implementation, 2026-09-19. M4 refines planned boundaries; no acceptance or full G1–G5 claim yet. Existing ADRs 005–010 remain in force.

## Acknowledgements and immutable content

Publisher: claim COMMIT → unchanged ledger wire bytes → positive publisher confirm without a correlated mandatory return → fenced local disposition COMMIT. Consumer: delivery with noAutoAck → validation → inbox/effects/projection COMMIT → individual ACK on the original live channel. A timeout/connection loss/COMMIT ambiguity is unresolved, never proof of remote rejection or rollback. Source ACK continues to mean staging only. Duplicate publication/redelivery is expected.

Canonical body, hash and wire encoding remain unchanged. messageId is event_id, contentType application/json, contentEncoding utf-8, deliveryMode 2, type revision-v1. Headers carry expected pipeline and application registration UUIDs; correlationId is a unique publication attempt UUID. These transport identities, delivery tags and channel incarnations are outside canonical content. No payload number is parsed through JavaScript Number. The publisher reads pipeline history, not mutable source/ES documents.

## Topology, identity and permissions

One retained single-node RabbitMQ 4.3.6-management instance, verified TLS, loopback/test-network endpoints, explicit memory/scheduler limits. Controlled setup creates one dedicated vhost, durable direct exchange, durable non-exclusive/non-auto-delete quorum queue and one exact routing binding. Names include one persisted application registration UUID. Queue arguments: x-queue-type=quorum, x-delivery-limit=-1, x-overflow=reject-publish, x-max-length-bytes=16777216. No message/queue TTL, expires or dead-letter routing. Broker max_message_size=131072. Heartbeat is explicitly 15 s.

The registration UUID is application-owned, not a broker-issued immutable queue identity. Metadata validation compares the intended names, durability, queue type/arguments, bindings and effective policies/configuration before enabling publication and on reconnection. Standard AMQP cannot detect an identically recreated queue. Intact retained storage, no unauthorized topology replacement/purge and trusted application code are assumptions. No marker-message scheme or multi-node HA claim.

Separate setup/admin, publisher, consumer and metadata-observer credentials. Publisher has write only on its exact exchange; consumer has read only on its exact queue, neither has configure rights or another vhost. RabbitMQ 4.3.1+ passive declaration requires any one of configure/write/read on that resource, so metadata checks do not justify configure access. Standard read also authorizes basic.get and queue.purge; this residual privilege is explicit and no application purge operation exists. The metadata observer can inspect only the dedicated vhost through the management API, without topology mutation rights. Actual selected-version permissions must be tested.

Initialization is not distributed-atomic. A privileged pipeline preparation persists the intended registration/topology/consumer identity, then setup creates/verifies those exact resources and finally binds the destination. A crash leaves a noneligible preparing target; resuming requires identical intended identity/configuration and verified resources. Runtime never creates/adopts/rebinds missing topology. Credentials/private CA and keys stay in run-owned private files, never artifacts or worker admin configuration.

Quorum delivery-limit is disabled deliberately for at least 25 repeated client crashes in finite acceptance. RabbitMQ 4.3 uses delivery-count: crashes/connection loss count as failed deliveries, while basic.nack does not increase that count; explicit rejects differ. Bounded prefetch/batches, cooldown, durable poison quarantine and ready-body budget limit this controlled use. Queue byte limits count ready bodies, exclude unacknowledged messages/overhead and can overshoot under concurrency; they are not exact total-storage limits.

## Forward pipeline schema and control functions

Migration pipeline/004-rabbitmq.sql preserves prior migrations/events/destinations/created timestamps and extends the existing RabbitMQ delivery_intents row, not a competing queue.

pipeline.rabbit_target: destination_id UUID PK/FK destinations; destination generation positive BIGINT; registration_id and consumer_id UUID UNIQUE; pipeline_id/source_epoch UUID bound to source_binding; vhost/exchange/queue/routing_key text; configuration JSONB object bounded 16 KiB with byte fingerprint; registered_at finite timestamptz; mode preparing/ready/cooldown/blocked; bounded block reason; failures BIGINT >=0; next_probe_at, probe_owner UUID, probe_generation BIGINT >=0, probe_until. Identity/configuration become immutable at preparation; only narrow functions change operational state. Destination receiver_identity is the application registration UUID, never a fabricated broker queue UUID. Existing ES binding/state is preserved.

RabbitMQ intents use pending/leased/retry_wait/satisfied, disposition broker_confirmed, their own rabbit_attempt_id UUID and settlement time. ES attempt/witness/remote_version columns and constraints remain ES-specific; no Rabbit row pretends to have an ES witness. Leased rows have owner UUID, positive monotonic BIGINT claim generation and finite lease; other rows have no current lease. A terminal intent is immutable. Partial due indexes and SELECT FOR UPDATE SKIP LOCKED allow independent workers. Generation overflow errors, never wraps.

pipeline.rabbit_attempts: attempt UUID PK; event/destination FKs; owner UUID and positive claim_generation; started_at/finished_at; channel incarnation UUID; outcome confirmed/transient/auth/configuration/integrity/expired; bounded diagnostic context. Composite intent/attempt FKs prevent cross-event evidence. Keep at most 32 recent nonterminal attempts per event while retaining the terminal evidence. This is bounded protocol diagnosis, not a full replay engine.

Restricted pipeline_rabbit can execute identity, claim, bounded wire read, renew, settle, admission and status only. READ COMMITTED claims commit before network I/O; all renew/settle/admission functions lock first and then read clock_timestamp. Destination generation, owner and current claim generation plus unexpired lease fence every result. Late observations cannot update newer work. Settle confirmed items independently. Infrastructure/nack failures persist retry_wait with positive exponential jitter (1 s base/30 s cap), never arbitrary-attempt DLQ. Authentication/routing/topology failures block the target. Cooldown has one fenced recovery probe; broker blocked stops publisher admission without stopping the separate consumer connection.

Existing structural assert_obligations/guards are deliberately migrated to accept valid progressed ES, RabbitMQ and consumer observation rows. Equal restaging verifies both intents and one observation exist and are valid; it never resets outcomes or repairs missing evidence. Canonical events remain immutable. Historical profiles still run older migrations and their original assertions.

consumer_observations retains event PK/FK and original created_at; adds pending/processed/quarantined, registered consumer/registration identities, exact content hash and retained receipt evidence/timestamp, plus next_check_at for fair pending scheduling. Positive processing and quarantine are distinct; quarantine is not a business effect. Terminal evidence is immutable. pipeline_receipts can select a bounded due list and record a matching explicit receipt only; it cannot publish or mutate source/events. Absent receipts remain pending and move to a later eligibility time, avoiding an allocation watermark and starvation. Consumer processing can precede local publisher settlement. SQL checks local identity/content; a trusted observer must actually read the independent consumer database—there is no cross-database FK or cryptographic proof of remote COMMIT.

## Independent consumer persistence and transactions

Create consumer_m4 as a separate database on the existing state PostgreSQL service. consumer_owner is a non-login owner; consumer_runtime and consumer_receipt_reader have only their respective allowlisted functions/CONNECT/USAGE, no source/pipeline access. Fixed SECURITY DEFINER search_path pg_catalog,pg_temp, qualified references and PUBLIC EXECUTE revocation in the same migration transaction apply throughout.

consumer.identity: immutable singleton consumer_id UUID, expected source_epoch/pipeline_id/registration_id UUID and codec pg18-jsonb-text/v1. consumer.processed_events: event_id text PK; epoch/entity_id/version unique with positive BIGINTs; mutation/baseline identity, deletion/time metadata; exact canonical body bytea/hash and processed_at; immutable, native SHA-256 and metadata/body/JSONB-object validation. No arbitrary numeric JSON parse in Node.

consumer.entity_projection: PK(epoch,entity_id), version and event reference; only strictly higher versions replace state, equal versions must have identical content; tombstones remain. consumer.mutation_effects: PK(epoch,source_change_id), unique inbox event FK; only captured mutations. consumer.entity_totals: PK(epoch,entity_id), nonnegative BIGINT mutation units. Each unique mutation inserts one audit row and one unit transactionally. Unseen older mutations still have effects; baseline fixtures have none. No external action or campaign subsystem.

One owned READ COMMITTED batch transaction validates/deduplicates at most 32 messages/1 MiB; acquire deterministic ordered per-entity advisory transaction lock keys (including absent projections), sorting actual lock keys to avoid avoidable inversions. Insert inbox with unique arbitration; after ON CONFLICT DO NOTHING use a fresh statement/snapshot to compare exact bytes/hash. New mutations add audit/unit, duplicates add neither. Project the highest version without losing intermediate effects. Real deadlocks/unknown transaction outcomes roll back or remain unknown and take no ACK path. No owner/session is shared concurrently or exposed to ordinary callers.

consumer.quarantine: stable raw-content plus relevant protocol-metadata digest key, exact raw body bytea <=128 KiB, bounded metadata bytes <=4 KiB, claimed identity, classification, bounded context and first-retained timestamp; compare bytes as well as hashes on duplicates, immutable. Transient availability/schema/configuration/unknown COMMIT errors are not poison. Only identifiable validation/content conflicts are quarantined. Invalid originals cannot overwrite a valid inbox record. Quarantine COMMIT precedes ACK, and retries cannot create effects. Bodies/metadata beyond supported retention bounds cause a fail-closed channel stop without positive ACK, never truncation.

A fixed read-only receipt operation accepts explicit bounded event IDs, returning immutable consumer identity and exact processing content, or bounded matching raw quarantine identity/content. Claimed messageId alone is insufficient to call the expected event quarantined. The observer compares actual retained content/protocol identity to its expected local event, including canonical bytes, not only a copied hash. No public HTTP/replay API.

## Client lifecycle and bounds

Use exact-pinned amqplib 2.0.1 public APIs with automatic recovery disabled. Verified TLS connection timeout, 15 s heartbeat, finite frame/channel limits and an AbortSignal-owned socket lifetime bound retirement; no undocumented driver internals. Install error/close/return/blocked/unblocked handlers before sends. publish() boolean indicates buffering/flow control, not broker confirmation: false stops further admission until drain, never republishes that already-buffered message. Track at most 128 current-channel attempts and 4 MiB bytes; a 10 s confirm deadline retires the channel and marks remaining outcomes unresolved. Correlate return by unique attempt correlationId (not eventId); a returned then positively confirmed message is unroutable, never success. Do not assume callback order. Late callbacks stay with their retired incarnation.

Leases are 30 s, renewed near 5 s via independent short owners while network/settlement is outstanding. Expiry cannot cancel remote work. One publishing batch in flight; tests use two processes. Request/result/log buffers and metadata HTTP responses are bounded. Stop signals stop admission and settle or leave recoverable work, without an unbounded promise/reconnect list.

Consumer uses its own independent AMQP connection, prefetch 64/global=false, one active database batch, <=32 messages/1 MiB and 25 ms flush. Retain original message objects/channel tokens through the transaction outcome. Only a confirmed successful owner return permits individual ACK (multiple=false) on that same still-live channel. No delivery tag crosses channel replacement. Database outage retires consumption and backs off, rather than tight-looping nack/requeue or quarantining valid data. Malformed neighbors can be isolated/quarantined while valid records progress; a rolled-back known integrity conflict may be isolated with bounded single-record transactions, but unknown COMMIT never becomes poison.

## Verification and limitations

MQ01–MQ16 and six healthy controls are independently inventoried before implementation/execution in scripts/required-rabbit-cases.ts. Real PostgreSQL, TLS broker, SIGKILL, queue/transaction observations and Toxiproxy faults are required. Verifier-owned mutation declarations/source receipts and independent SQL compare exact inbox/effects/totals/projections, ES expectations and consumer receipts; counters/production normalization alone are insufficient. Synthetic baseline and poison/corruption controls are labeled and isolated. Every new private boundary surrounds actual work; no business API exposes process control.

This provides durable at-least-once transport with once-per-unique-event database effects under stated retention/ownership assumptions, not distributed exactly-once transport, external-effect safety, HA, unlimited buffering, source-scale capacity or complete Optio guarantees. Preserve the known baseline/no-op command-FK obligation for later seeding; no baseline activation occurs now.

Implementation clarification, 2026-09-19: target retry eligibility and per-item retry eligibility are independently jittered. The real MQ10 scheduling reproduction showed that taking a recovery-probe lease before finding eligible work can leave an empty probe occupied for 30 seconds. Forward migration 005 allocates that probe only after SELECT FOR UPDATE SKIP LOCKED has selected its one eligible row. An empty claim therefore preserves unoccupied admission. This is a correction to the new M4 implementation, not a change to the planned acknowledgement boundary.
