## Implementation, environment and assumptions

M4 extends the existing RabbitMQ obligation and creates the separate `consumer_m4` database on the existing state PostgreSQL service. Source ACK still means staged. Only a positive broker confirm without a correlated mandatory return permits fenced `broker_confirmed` settlement; this says nothing about consumer processing. Only successful inbox/effect/projection COMMIT permits individual ACK on the original live channel. Ambiguity permits duplicate publication/redelivery, not speculative success. The consumer commits one audit effect and aggregate unit per unique captured mutation; quarantine is diagnosis, not business success.

Additive migrations are `migrations/pipeline/004-rabbitmq.sql`, corrective `005-rabbit-probe.sql` and `migrations/consumer/001-consumer.sql`. Earlier source/pipeline migrations and source/ES implementation remain unchanged. [ADR 011](../adr/011-rabbitmq-consumer.md) records SQL types/constraints/grants, transaction ownership, topology, limits and trust assumptions. SPEC receives only the authorized M4 refinement. Runtime source/pipeline/consumer credentials remain separate; consumer credentials cannot connect to source or pipeline databases. Canonical eleven-field bytes and codec are unchanged.

RabbitMQ `4.3.6-management` was pulled/tested at `sha256:de62d9901fb73aaa8767b9c1e9ea32f2938f69d1b83e430f7c5ca854081d2128`. `amqplib` is exactly `2.0.1`, the only added package. Node `24.19.0`, npm `12.0.2`, TypeScript `5.9.3`, pg `8.23.0`, ES client `9.5.1` and existing quality pins remain unchanged. Docker was `29.7.2`, Compose `5.5.1`. Retained service pins are:

- PostgreSQL `18.6-bookworm@sha256:1c59e2c3c818eaa0f0628f695b36e7c9e362d6b219b36a54a32df645cbd7e1af`.
- Elasticsearch `9.5.4@sha256:82ac14f43fe701992e601f4cc81e1c0d7dbc5a2576d8cd736006452925df4026`.
- Toxiproxy `2.12.0@sha256:9378ed52a28bc50edc1350f936f518f31fa95f0d15917d6eb40b8e376d1a214e`.

The local Linux prerequisite was already `vm.max_map_count=1048576`; no host setting changed. CI retains explicit disposable GitHub-hosted VM provisioning and selects the same `make verify-m4`, with a 55-minute job bound. Local workflow validation is not hosted execution. Broker memory is bounded at 1 GiB, ES at 2 GiB/Xmx1 GiB, with run-owned loopback ports/private TLS configuration.

The single-node broker has an application-owned registration UUID, vhost, durable direct exchange and quorum queue: no TTL, delivery-limit -1, reject-publish and 16 MiB ready-body budget. It is not a broker-issued immutable queue UUID; metadata checks cannot detect identical administrative recreation. Standard consumer read permission also permits basic.get/purge, and runtime exposes no purge operation. Intact storage and no unauthorized topology replacement/purge are assumptions. Ready-body limits exclude unacknowledged bodies/overhead and may overshoot; no HA or exact total-storage claim is made.

Publisher bounds are 128 outstanding messages/4 MiB, 10-second confirm deadline, 30-second claims renewed near 5 seconds and a 15-second heartbeat. Consumer prefetch is 64, with one active database batch of at most 32 messages/1 MiB and a 25 ms flush. Broker message cap is 128 KiB; quarantine retains full raw bytes to that cap and relevant metadata to 4 KiB. Oversized unsupported traffic fails closed. Attempts, diagnostics, HTTP responses, output and disposal are bounded. Ordered AMQP close has an independent deadline and owned-socket abort, consuming late completion/rejection.
