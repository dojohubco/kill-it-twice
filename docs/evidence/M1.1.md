## Transaction ownership and outcomes

A Source owns connection configuration and allows one active transaction. Each transaction owns a new private session, closes it before returning, and gives the callback only create/mutate/fixed inspection operations. The capability expires after the callback. Nested/concurrent calls fail before SQL; callers wanting one atomic unit use the existing capability. No arbitrary client or manual transaction-control operation is exposed.

Success requires a confirmed COMMIT command tag. Known rollback, unknown COMMIT, failure before work starts, and confirmed commit followed by cleanup failure are distinct. A successful cleanup ROLLBACK cannot settle an earlier ambiguous COMMIT. Errors preserve the primary cause and PostgreSQL SQLSTATE separately from cleanup failures. Unknown completion or broken cleanup poisons the owner. There is no mutation retry or command-idempotency API. Pure transport fixtures cover connect, BEGIN, ROLLBACK, COMMIT and close failures; they supplement the real PostgreSQL regressions.

The real deadlock uses two entities, separate owned sessions and reciprocal barriers after each writer has mutated its first entity. It requires exactly one actual **40P01** victim and one survivor. Victims were writer **1, 1, 0** across the three final runs. Independent observations showed both entities at version **2**, only initial and survivor payloads in each history, and no victim revision. Ordinary success/rollback, expired capabilities and sequential owner reuse also passed.

Source trigger capture and restricted runtime roles still enforce the three-table contract. The retained T01–T07 tests exercise lifecycle, exact BIGINTs, constraints, outbox-side errors, row-lock waiting, immutable history, actual login permissions and known allocation/commit-order inversion. A maximum allocation ID remains an invalid commit watermark.
