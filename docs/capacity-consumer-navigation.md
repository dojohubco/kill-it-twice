# Consumer export navigation and replica comparison

2026-09-22. This is a measured follow-up plan, not an implemented optimization result. The existing 131,072-baseline/page64 run at `9c63b8b` completed independently reconciled with cleanup. No data or worker setting was changed during it.

Two read-only plans taken after that run had quiesced its workers show a remaining diagnostic-export problem. At entity cursor 65,536, the `entity_totals` 32-row page scanned the 131,072-row table and sorted the matching half (30.157 ms). The corresponding `entity_projection` page used parallel scan/sort (19.889 ms). Exact plans are retained in `artifacts/capacity/continuation-20260922T1725/consumer-navigation-plans.json`. These two diagnostic reads add small measurement interference during export; they are not a pure application-throughput benchmark.

Add only non-unique `entity_id` indexes to those two consumer tables through a forward migration. Keep their epoch/entity primary keys, all queries and returned fields, constraints, trigger/function identities, permissions, mutation effects and current projection behavior unchanged. Do not filter exports to hide an unexpected epoch or remove an independent oracle check. The index is installed during controlled initialization/maintenance, not claimed to be a concurrent zero-downtime migration.

A populated old-image fixture must compare all consumer rows and function/constraint/trigger/ACL metadata exactly, compare full pre/post export bytes, observe actual index plans, and verify runtime index administration is denied. The source/receiver oracle then reconciles all 4,096 fixture baselines independently. The functional real-fault gate remains required on the new code.

After that proof, a capacity-only optional one-or-two-process setting may scale ES delivery, publication, consumption and receipt observation in the owned test project. Normal runtime defaults, per-worker byte/count/lease bounds and permissions remain unchanged. Record exact replicas and existing memory limits. Compare 131,072 baselines with four scanners/page64 before increasing count; additional processes may contend and consume more memory, so improvement is a hypothesis. A result needs complete independent reconciliation and cleanup, not only counters or a lower scan duration. No additional service, dependency, connection pool, mutation semantics or host tuning is planned.
